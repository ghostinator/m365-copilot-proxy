## Prioritized findings

### P1 — Auth failure does not prevent the standalone server from reporting healthy

**Source:** `packages/proxy/plugins/auth.ts:8`, `packages/proxy/routes/health.get.ts:3`, `packages/proxy-lib/src/index.ts:24`.

The plugin's comment promises that an authentication failure aborts boot. In the installed Nitro version's generated runtime, `runNitroPlugins` calls `plugin(nitroApp)` without awaiting the returned promise. The async rejection is logged as an unhandled rejection while the HTTP listener remains alive. `/health` is an unconditional static response.

**Reproduced:** with deliberately nonexistent cache/secrets paths and interactive auth disabled, the built launcher logged `Auth failed`, remained running, and returned HTTP 200 with `{"status":"ok"}`. Repeated in loopback and default-bind modes. No Microsoft call was needed.

**Impact:** a service manager, installer or user can see a healthy process that cannot serve completions. Restart-on-failure will not repair it because the process has not failed.

**Fix:** explicitly await required auth before listening, or track initialization and gate requests. Keep liveness separate from readiness: `/health/live` can report process availability; `/health/ready` should return 503 when auth is unavailable. Readiness must inspect local state, not issue billable/live chat probes. Add a built-server test, since fetch-app tests cannot catch the Nitro lifecycle mismatch.

### P1 — The standard launcher exposes an unauthenticated API on all interfaces

**Source:** `packages/proxy/bin/m365-proxy.mjs:7`, `packages/proxy/nitro.config.ts`, `packages/proxy/middleware/cors.ts:8`, `packages/proxy-lib/src/index.ts:60`.

The launcher sets a port but no default host. The generated Node server passes an undefined host to `listen`. **Reproduced:** with both host variables absent, it printed `Listening on http://[::]:<port>`. The API has no incoming key validation and permits cross-origin requests. Actual remote reachability still depends on firewall/network configuration.

The NixOS module and local Windows wrapper already default to `127.0.0.1`; the direct launcher does not. This inconsistency matters when users follow the standalone README or install a service around the binary.

**Fix:** default the actual server entry point to loopback. Require an explicit host setting for LAN use, support bearer-token validation consistently in both serving paths, and make allowed origins configurable. Verify the listener and unauthorized requests against the built artifact.

### P1 — Conversation identity can mix independent sessions

**Source:** `packages/proxy-lib/src/handler.ts:205–283`.

The key is a 32-bit hash of the first user's text and sorted tool names. The reuse guard only checks message count. It does not establish that the incoming history extends the exact history previously served. System prompts, working-directory context, image contents and client identity are absent from the key. There is also no per-conversation lock across formatting, upstream execution and state updates.

**Reproduced:** an unrelated four-message history reused the same state and conversation ID as a different chat with three messages already recorded. Distinct opening strings `Aa` and `BB` also produced the same state due to a deterministic hash collision. These are local state reproductions, not a live demonstration of leaked model content.

**Impact:** a long-running service used by several clients can send a delta into the wrong server-side history; simultaneous requests can race on the same mutable state. Adding tool names upstream reduced one collision class but did not establish session identity.

**Fix:** support explicit client conversation IDs, scope them to authenticated callers when auth is enabled, and verify complete history prefixes for fallback inference. Use a collision-resistant digest and bounded history records. Serialize the whole transaction per conversation; a turn-budget admission queue alone does not serialize upstream turns. Test identical greetings, different system prompts/images, divergent histories, retries and simultaneous requests.

### P1 — A socket close before the handshake leaves the request pending

**Source:** `packages/core/src/session.ts:378`, `:627`, `:633`.

The outer `chat()` promise resolves only after `sendChat`, or rejects on selected error paths. The socket's `close` handler only calls the stream's `onDone`. If the connection closes without an error before the handshake, no stream was returned, so the caller remains blocked. The code also has no general handshake/turn deadline; its only timer is the two-second abort close fallback.

**Reproduced:** `scripts/review/offline-session.test.ts` supplies a fake socket that closes before a handshake, then observes the promise still pending. The test reproduces current behavior; it is not a passing correctness test for a fix.

**Fix:** reject any pre-stream close, settle each phase exactly once, add configurable connection/handshake/idle/overall deadlines and propagate cancellation through auth, uploads and downloads. SSE keepalives should not keep a broken upstream turn alive indefinitely.

### P1 — A publish failure can delete a shared Copilot Studio agent

**Source:** `packages/core/src/agent.ts:369–390`.

The catch for *any* `publishBot` failure deletes the bot and recreates it. A transient publish error for a bot discovered in the shared tenant can therefore remove another host's active agent. This contradicts the documented rule that shared agents are never deleted.

**Evidence level:** direct source finding; no tenant mutation was performed to prove it live.

**Fix:** preserve discovered agents on publish failure, distinguish transient errors from invalid resources, and provision a replacement without removing the shared bot. A mocked publish failure can verify that no DELETE occurs.

### P1 for service use — The local Windows task does not supervise the server

**Local files:** `scripts/windows/Install-ScheduledTask.ps1:50–54`, `Start-Proxy.ps1:87–101`, `Stop-Proxy.ps1:16–31` in the original workspace.

The scheduled action runs `Start-Proxy.ps1`, which launches another PowerShell process with `-NoExit` and `-WindowStyle Normal`, then exits. The recorded PID belongs to that shell, not Node. If Node fails, the shell may remain open; the 500 ms `HasExited` check cannot establish server readiness. Task Scheduler sees the launcher complete rather than tracking the server lifetime. No restart policy is set. The principal is an interactive user and the trigger is logon, so this is not a boot-time service before login.

**Additional confirmed details:** constructing the script's exact `New-ScheduledTaskSettingsSet` locally returned `RestartCount=0`, `ExecutionTimeLimit=PT72H`, and `MultipleInstances=IgnoreNew`. The 72-hour default is an additional issue to fix when the action is changed to stay attached; today it does not reliably bound the detached child. `-NoInteractive` merely omits setting the opt-in variable; it does not clear an inherited `M365_ENABLE_INTERACTIVE_APPROVAL=1` or force `M365_NO_INTERACTIVE=1`.

`Stop-Proxy.ps1` trusts a PID file and force-kills the process tree without checking executable/command/start time. A stale PID reused by another process can target the wrong application. This was identified by source inspection, not by killing a process.

**Fix:** give Task Scheduler a foreground runner with a propagated Node exit code, no visible console, explicit working directory/environment, restart policy, unlimited execution duration and a single-instance policy. Check readiness with a deadline. Stop by verified process identity and prefer graceful shutdown. Run interactive sign-in separately under the same user.

### P2 — Windows turn-budget log paths are split incorrectly

**Source:** `packages/core/src/turn-budget.ts:110`.

`M365_BUDGET_LOGS` is split on `:`, which splits Windows drive letters. **Reproduced:** `C:\logs\one;D:\logs\two` became `C`, `\logs\one;D`, and `\logs\two`. Even one `C:\...` path breaks.

**Fix:** support a structured array or the platform's path delimiter (`;` on Windows), document compatibility for the existing POSIX format, and add native-drive/space/UNC cases. Missing external logs make the estimated account budget less reliable; this does not prove every Windows request throttles.

### P2 — OpenClaw setup can overwrite existing configuration after a parse error

**Source:** `packages/openclaw-plugin/src/setup.ts:41–64`.

If parsing an existing config throws, setup continues with `{}` and overwrites the original file. Any unsupported format or malformed JSON can therefore remove unrelated providers/settings. Even valid configuration is written directly without a backup or atomic replacement.

**Evidence level:** source finding; the user's configuration was not opened or changed.

**Fix:** fail without writing on parse/schema errors, show the proposed merge, back up the existing file, and atomically replace only validated configuration. Test preservation of unknown fields and parse failures.

### P2 — Windows tests fail, and the publication workflow does not run tests

**Source:** `packages/core/src/log.test.ts:29–32`, `scripts/bench/turn-budget.test.mjs:127–131`, `.github/workflows/publish.yml`.

The stock suite on this machine produced **413 passed, 2 failed, 6 skipped** across 19 test files. Both failures compare POSIX absolute strings to Windows-resolved paths. These appear to be test portability defects, separate from the real drive-letter parsing bug above. The baseline build passed.

The sole tracked workflow builds and publishes on a published release; it does not run tests or check pull requests. No clean-machine Windows installation gate exists.

**Fix:** use native absolute-path fixtures, add Windows/Linux validation, run the existing suite before publication, and smoke-test the exact packed runtime outside the workspace. Ensure no test requires real credentials or M365 quota by default.

## Other development opportunities

- **Reliable auth persistence:** `saveCache` catches and ignores write failures. A service can authenticate once while failing to persist its token cache and then fail after restart. Add atomic persistence, actionable errors and permission checks. The current writes do not explicitly request restrictive file modes/Windows ACLs. Keep the legacy `~/.config/opencode-m365` path compatible.
- **One auth owner:** only `getToken` has an in-flight guard; additional scopes can independently open the same persistent browser profile. A future service should coordinate profile access across scope requests and detect a second process using that profile. Reproduce with mocked profile locking before changing login behavior.
- **Operational logging:** `createLogger.error` is disabled unless debug/trace is enabled, and stdout logging alone does not enable it. Add always-on bounded operational errors, optional structured stdout, redaction, rotation and an exportable diagnostic bundle that excludes tokens, browser state and prompt content by default.
- **Bounded resources:** the pool has idle eviction on resolve but no maximum size. Image upload and artifact fetch paths lack timeout/size limits and do not accept the request's abort signal. Plan explicit limits, backpressure and a draining shutdown path before shared-service use.
- **Consistent capability metadata:** `/v1/models` advertises 1M input/output hints; OpenClaw config uses 128k/16,384 and text-only input. The handler accepts `temperature` and `max_tokens` but does not use them. Publish a clear compatibility contract and derive supported client metadata from one registry; do not infer real model context limits from acceptance or synthetic hints.
- **Windows setup details:** the local setup script accepts Node 22 while the upstream README specifies 24+. Its fallback browser install uses `$pwVersion` in the branch where that variable was never assigned. The start script's help labels `::` as IPv6 loopback; `::1` is loopback and `::` is the wildcard. Align requirements, validate port/path inputs and avoid constructing shell code from paths and bind strings.
- **Docs organization:** preserve the research notebook, but put current installation, operation and recovery instructions in a short operator guide. Distinguish historical findings from current defaults, especially agent usage and throttle explanations. The later turn-budget work refines earlier thread-rate-only claims; no new throttle experiments were run in this review.
- **Research boundaries:** native MCP/Dataverse tool calling remains the documented closed path. Do not reopen it as part of service packaging. Preserve prompt-emulated routing and use the existing real pi harness for later behavior changes.

## Recommended Windows delivery design

Start with a **per-user background installation**. It reuses the user's working MSAL/browser state and supports manual MFA when a tenant requires it. A true Windows service running before anyone signs in should be a separate deployment mode, with an explicitly chosen service identity, private writable state and a documented reauthentication process. Running as LocalSystem would change the profile and does not automatically inherit the current user's login.

Proposed command surface, to be implemented rather than implied to exist today:

```text
m365-proxy setup
m365-proxy login
m365-proxy doctor
m365-proxy serve
m365-proxy service install
m365-proxy service status
m365-proxy service start
m365-proxy service stop
m365-proxy service uninstall
```

`setup` checks the supported Node version, provisions the exact matching browser if needed, selects port/host and validates writable storage. `login` is the explicit human step. `doctor` is local/read-only by default, with an optional clearly labelled one-turn live verification. `serve` is a foreground process suitable for a supervisor. Service commands manage a per-user task initially; use a service wrapper/SCM integration later if pre-login operation is required. Plain Node is not itself an SCM service executable.

Install versioned application files under `%LOCALAPPDATA%\Programs\M365CopilotProxy\<version>`, outside the source checkout. Preserve current auth state in its legacy location. Add a configurable data-root abstraction with explicit migration support rather than silently relocating caches. Keep browser profiles separate from app versions so an upgrade does not invalidate them.

Ship the prebuilt Nitro `.output`, launcher and a release manifest. A portable ZIP can include an approved/pinned Node runtime, with browser provisioning during setup; a later installer can provide shortcuts and uninstall integration. The browser cache/native executable remains an external runtime dependency even though the JS artifact includes Playwright packages. Verify artifact manifests, runtime/browser versions and downloaded checksums. Users should not need Git, pnpm, a compiler, Nix or the benchmark dependencies just to run a release.

Updates should download/extract into a new version directory, run local validation, stop/drain the old runner, switch the target, restart and verify readiness. Retain the last working version for rollback and leave auth/user configuration intact. Uninstall should stop/remove startup registration and application files; deleting account state should be an explicit separate option.

## Implementation order and acceptance criteria

| Order | Work | Done when |
| --- | --- | --- |
| 1 | Startup auth/readiness, loopback default, socket settlement/deadlines | Built server cannot claim ready without auth; default listener is loopback; early-close and stalled-upstream tests terminate predictably |
| 2 | Conversation isolation and shared-agent preservation | Divergent clients cannot share state; concurrent same-session requests serialize; transient publication failure never deletes a discovered bot |
| 3 | Unified setup/login/doctor/serve CLI and Windows runner | A clean Windows user can install, sign in, start, inspect logs, stop and recover without editing scripts; auth expiry gives an actionable status |
| 4 | Versioned portable release and supervised startup | No source checkout required; a killed Node child is restarted; logout/reboot behavior is documented; update/rollback retains state |
| 5 | CI and release gates | Windows/Linux unit tests and packed-artifact smoke tests pass; failed checks block publication |
| 6 | Optional pre-login service and local status UI | Explicit service identity and recovery flow validated; status page reports auth/readiness/quota without spending chat turns |

Useful later experiments: a 24–72 hour restart/idle/resume soak; service-account cache refresh across reboot; browser version upgrade/rollback; reconnect and cancellation through a simulated network outage; and one short sequential real-pi task on the final installed artifact. Pre-register expected outcomes, retain sample sizes and cooldowns, and separate offline lifecycle tests from quota-consuming model tests.
